code block ها و admonition ها
code block ها نگه داشته می‌شوند (<pre>): مخاطب این جست‌وجوگربرنامه‌نویس Django است و اکثر پرسش‌های فنی بدون مثال کد پاسخ کاملندارند. برچسب‌های headerlink و شماره‌ی خطوط حذف شده‌اند تا کد تمیز بماند.
باکس‌های admonition (note/warning/versionadded) حذف نمی‌شوند و بابرچسب نوعشان در متن علامت‌گذاری می‌شوند (مثل [warning] ...): اینباکس‌ها اغلب هشدارهای امنیتی یا اطلاعات سازگاری نسخه‌ها را دارند که در پاسخ به پرسش‌های فنی ارزشمند است. در نسخه‌ی اولیه حذفشان کردم،اما با مرور صفحات به این نتیجه رسیدم که اطلاعات مفیدی از دست می‌رود.

برای مدل از all-MiniLM-L6-v2 استفاده کرم چون می تونه جمله رو با 384 بعد مپ کنه و مخصوص semantic sreach هست.
ما می خوایم اگر صفحه حذف شد داده های اون هم از بین برین پس به ON DELETE CASCADE نیاز داریم.
استفاده از بخش UNIQUE (page_url, chunk_index) برای یونیکنس و جلوگیری از ورود داده های تکراری هست.

چرا مرز سرفصل را رعایت می‌کنیم؟ چون مستندات فنی، هر بخشِ زیر یک سرفصل درباره‌ی یک موضوع مشخصه — چانکی که دو تا سرفصل نامرتبط رو قاطی کنه، برای embedding نویز می‌سازه. heading_path هم به بازیابی کمک می‌کنه (مثلاً «Sessions > Technical details» خودش سیگنال معنایی داره)

 تصمیم گرفتم تا overlap رو روی 150 بذارم تا از نظر همپوشانی داده ها یک نسبت بهینه داسته باشیم.

 درمورد چانکها:
هزینه: تعداد چانک بیشتر برابر با امبدینگ بیشتر میشه
فرصت: هر چانک تک موضوعی باشه، یعنی یک سشن = با یک مبحث
هزینه: چانکهای کوچیک با محتوای کم زیاد میشن
فرصت: باعث میشه چانکها تمیزتر و معنادار تر باشن
هزینه: ممکنه در هنگام بازیابی به مطالب کم و کوچیک برگردونه
فرصت: یک مرز موضوعی برای داده ها به وجود میاد
