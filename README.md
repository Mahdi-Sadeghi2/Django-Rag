## Code Block و Admonition

### Code Block

`code block`ها حذف نمی‌شوند و به همان شکل `<pre>` نگه داشته می‌شوند.

دلیلش اینه که مخاطب این جستجوگر، برنامه‌نویس‌های Django هستن و خیلی از سؤال‌های فنی بدون مثال کد جواب کاملی ندارن.

برای تمیزتر شدن کد:

* `headerlink`ها حذف می‌شوند.
* شماره‌ی خطوط حذف می‌شود.
* خود کد حفظ می‌شود.

---

### Admonition

باکس‌های `note`، `warning` و `versionadded` هم حذف نمی‌شوند.

نوع هر باکس داخل متن مشخص می‌شود:

```text
[warning] ...
```

این بخش‌ها معمولاً اطلاعات مهمی مثل **هشدارهای امنیتی، نکات مهم یا سازگاری نسخه‌ها** دارن.

در نسخه‌ی اولیه تصمیم گرفته بودم این بخش‌ها رو حذف کنم، اما بعد از بررسی صفحات متوجه شدم که با این کار بخشی از اطلاعات مهم مستندات از بین میره.

---

## مدل Embedding

برای ساخت Embedding از مدل:

```text
sentence-transformers/all-MiniLM-L6-v2
```

استفاده کردم.

این مدل متن رو به یک Vector با **384 بُعد** تبدیل می‌کنه و برای کارهایی مثل **Semantic Search** مناسبه.

در این پروژه هم هدف ما اینه که سؤال کاربر و متن مستندات رو به Vector تبدیل کنیم و بعد میزان شباهتشون رو بررسی کنیم.

---

## حذف خودکار داده‌های مرتبط با Page

اگر یک Page از دیتابیس حذف بشه، می‌خوایم تمام Chunkهای مربوط به اون Page هم حذف بشن.

برای همین از:

```sql
ON DELETE CASCADE
```

استفاده کردیم.

در نتیجه رابطه به این شکل کار می‌کنه:

```text
Page حذف می‌شود
       ↓
Chunkهای مربوط به Page
       ↓
به صورت خودکار حذف می‌شوند
```

این کار باعث می‌شه داده‌های اضافی و بدون مرجع داخل دیتابیس باقی نمونن.

---

## جلوگیری از داده‌های تکراری

برای جلوگیری از ذخیره‌ی دوباره‌ی یک Chunk از این ترکیب به عنوان مقدار `UNIQUE` استفاده کردیم:

```sql
UNIQUE (page_url, chunk_index)
```

یعنی یک `page_url` نمی‌تونه دو بار با یک `chunk_index` یکسان ذخیره بشه.

# انتخاب Overlap

برای Chunkها مقدار `overlap` رو روی **150** قرار دادم.

هدف اینه که بین دو Chunk مقداری از متن مشترک باقی بمونه تا اگر یک مفهوم دقیقاً در مرز دو Chunk قرار گرفت، اطلاعات اون مفهوم به طور کامل از بین نره.

به صورت ساده:

```text
Chunk 1
████████████████████
              ████████████████
              Chunk 2
```

این همپوشانی باعث می‌شه ارتباط بین Chunkهای پشت سر هم بهتر حفظ بشه.

# تصمیم‌گیری درباره Chunkها

در انتخاب اندازه و مرز Chunkها چند نکته وجود داشت:

| هزینه                                                         | فرصت                                         |
| ------------------------------------------------------------- | -------------------------------------------- |
| تعداد Chunk بیشتر → Embedding بیشتر                           | هر Chunk می‌تونه روی یک موضوع مشخص تمرکز کنه |
| Chunkهای کوچک → محتوای کمتری در هر Chunk                      | Chunkها تمیزتر و معنادارتر می‌شن             |
| Chunkهای خیلی کوچک ممکنه هنگام Retrieval اطلاعات کمی برگردونن | مرز مشخص‌تری بین موضوعات ایجاد می‌شه         |

بنابراین هدف فقط کم کردن تعداد Chunkها نیست.

هدف اینه که بین **اندازه، هزینه و کیفیت اطلاعات** تعادل ایجاد کنیم.

# چرا از `1 - cosine distance` استفاده کردیم؟

`pgvector` هنگام مقایسه‌ی دو Embedding، مقدار **Cosine Distance** رو برمی‌گردونه، نه مستقیماً مقدار Similarity.

در Cosine Distance:

```text
Distance کمتر
      ↓
متن‌ها به هم نزدیک‌تر
      ↓
Similarity بیشتر
```

ولی ما برای نمایش نتیجه، یک امتیاز Similarity می‌خوایم که برعکس باشه:

```text
Similarity بیشتر → شباهت بیشتر
Similarity کمتر → شباهت کمتر
```

برای همین از این فرمول استفاده کردیم:

```text
similarity = 1 - cosine_distance
```

مثلاً اگر:

```text
cosine_distance = 0.1
```

داشته باشیم:

```text
similarity = 1 - 0.1
           = 0.9
```

یعنی دو متن شباهت زیادی به هم دارن.

# چرا برای Query و Document از یک مدل استفاده کردیم؟

وقتی کاربر سؤالش رو وارد می‌کنه، سؤال باید به Embedding تبدیل بشه.

از طرف دیگه، متن‌های موجود در دیتابیس هم قبلاً به Embedding تبدیل شدن.

برای اینکه این دو قابل مقایسه باشن، باید در یک **فضای مشترک** قرار داشته باشن.

برای همین در این پروژه هم Query و هم Document با یک مدل ساخته می‌شن:

```text
sentence-transformers/all-MiniLM-L6-v2
```

فرایند به این شکل هست:

```text
User Query
    ↓
Embedding Model
    ↓
Query Vector
    ↓
       pgvector
    ↑
Document Vectors
    ↑
Embedding Model
    ↑
Documents
```

حالا `pgvector` می‌تونه Query Vector رو با Vectorهای موجود در دیتابیس مقایسه کنه و نزدیک‌ترین Chunkها رو پیدا کنه.

# خطای `vector <=> numeric[]`

در طول پیاده‌سازی با این خطا مواجه شدم:

```text
operator does not exist: vector <=> numeric[]
```

مشکل از اینجا بود که `psycopg2` لیست Python رو به صورت آرایه‌ی PostgreSQL یعنی `numeric[]` ارسال می‌کرد.

در حالی که عملگر `<=>` در `pgvector` انتظار یک مقدار از نوع `vector` داشت.

برای حل مشکل، نوع داده رو هنگام ارسال Query به PostgreSQL به `vector` تبدیل کردم.

به زبان ساده:

```text
Python List
    ↓
psycopg2
    ↓
numeric[]
    ❌
```

در حالی که PostgreSQL انتظار داشت:

```text
Python List
    ↓
Cast به vector
    ↓
pgvector
    ✅
```

# تست عملکرد Search

بعد از پیاده‌سازی بخش‌های اصلی، یک فایل تست نوشتم تا عملکرد سیستم رو با **۳ سؤال مختلف** بررسی کنم.

هدف تست این بود که ببینیم:

1. آیا سؤال کاربر به Chunk درست می‌رسه؟
2. نتایج چقدر به سؤال نزدیک هستن؟
3. آیا نتیجه‌ی موردنظر در بین `Top-k` نتایج قرار می‌گیره؟
4. امتیاز Similarity چقدر قابل اعتماد به نظر می‌رسه؟

خروجی این تست در ادامه بررسی شد تا مشخص بشه سیستم در چه سؤال‌هایی خوب عمل می‌کنه و کجاها نیاز به بهبود داره.



# کجا خوب جواب داد و چرا؟

## تحلیل نتایج جستجو

برای بررسی عملکرد **Semantic Search**، دو سؤال مختلف رو تست کردم.

---

## سؤال ۱: Middleware

نتایج:

```text
[0.675] Middleware > Other middleware hooks
[0.537] Middleware > Writing your own middleware
[0.514] Middleware
```

هر سه نتیجه مربوط به صفحه‌ی درست بودن.

نکته‌ی جالب این بود که بخش **Writing your own middleware** که دقیقاً به سؤال مربوط می‌شد، رتبه‌ی اول رو نگرفت.

دلیلش اینه که جستجوی Semantic بر اساس **معنی متن** کار می‌کنه، نه فقط تطبیق کلمات.

در نتیجه، با بررسی ۳ نتیجه‌ی اول (**hit@3**) عملکرد جستجو خوب بود، چون صفحه‌ی درست بین نتایج وجود داشت.

---

## سؤال ۲: `get_absolute_url`

نتایج:

```text
[0.520] URL dispatcher
[0.518] shortcuts > resolve_url()
[0.505] shortcuts > redirect()
```

اینجا نتیجه خیلی ضعیف‌تر بود.

صفحه‌ای که انتظار داشتم یعنی **Models** اصلاً بین نتایج نبود؛ در حالی که `get_absolute_url` در همین بخش توضیح داده شده.

### چرا این اتفاق افتاد؟

امتیاز نتایج همگی نزدیک به هم بودن:

```text
0.520
0.518
0.505
```

یعنی جستجو نتونسته با اطمینان نتیجه‌ی مناسبی پیدا کنه.

احتمالاً دلیلش اینه که:

* Chunk مربوط به `get_absolute_url` در بین متن‌های زیادی درباره‌ی Model قرار گرفته.
* در نتیجه، مفهوم `get_absolute_url` داخل متن بزرگ‌تر گم شده.
* عنوان Chunk هم احتمالاً به صورت مستقیم `get_absolute_url` نبوده.

### نتیجه

این تست نشون داد که **کیفیت Chunking تأثیر مستقیمی روی Semantic Search داره.**

حتی اگر اطلاعات موردنظر داخل دیتابیس وجود داشته باشه، اگر Chunkها درست ساخته نشده باشن، ممکنه جستجو نتونه اون اطلاعات رو پیدا کنه.

---

## چیزی که از این تست یاد گرفتم

فقط داشتن Embedding و Vector Search کافی نیست.

کیفیت نتیجه به چند مرحله وابسته است:

```text
Document
   ↓
Chunking
   ↓
Embedding
   ↓
Vector Search
   ↓
Ranking
   ↓
Answer
```

اگر Chunking خوب نباشه، حتی یک عبارت مهم مثل `get_absolute_url` هم ممکنه در جستجو پیدا نشه.

**پس قبل از اینکه سراغ تغییر مدل Embedding یا الگوریتم Search برم، باید کیفیت Chunkها رو بررسی کنم.**


چرا inputSchema اینقدر مهمه؟ چون مدل زبانیِ کلاینت فقط با همین توضیح‌ها تصمیم می‌گیره کدوم ابزار رو کی صدا بزنه



## نکات طراحی و تصمیم‌های فنی

### 1. چرا `answer` بدون LLM خارجی پیاده‌سازی شد؟

طبق تسک، اگر دسترسی به یک مدل زبانی خارجی وجود نداشته باشد، می‌توان از همان تابع Retrieval استفاده کرد و نیازی به پیاده‌سازی LLM نیست.

به همین دلیل، `answer` در این پروژه به صورت **Extractive** پیاده‌سازی شده است.

یعنی به جای اینکه مدل زبانی پاسخ جدیدی تولید کند، اطلاعات مرتبط را مستقیماً از نتایج Retrieval برمی‌گرداند:

```text
User Question
     ↓
Retrieval
     ↓
Relevant Chunks
     ↓
Answer + Source URL
```

این روش باعث می‌شود پاسخ‌ها مستقیماً به محتوای پیدا‌شده متکی باشند و منبع هر بخش نیز مشخص باشد.

---

### 2. چه زمانی می‌گوییم «اطلاعات کافی پیدا نشد»؟

برای جلوگیری از ارائه‌ی نتایج ضعیف، یک حداقل امتیاز برای Similarity تعریف شده است:

```python
MIN_CONFIDENCE = 0.45
```

این مقدار به صورت تصادفی انتخاب نشده است.

در ارزیابی انجام‌شده، پایین‌ترین امتیاز مربوط به یک نتیجه‌ی موفق حدود:

```text
0.483
```

بود.

بنابراین مقدار `0.45` به عنوان یک Threshold اولیه انتخاب شد تا اگر نتیجه‌ی بازیابی‌شده امتیاز بسیار پایینی داشت، سیستم به جای ارائه‌ی یک پاسخ نامطمئن، به کاربر اعلام کند که اطلاعات کافی پیدا نشده است.

> این Threshold بر اساس نتایج Evaluation فعلی انتخاب شده و با داده‌های بیشتر می‌تواند در آینده دوباره تنظیم شود.

---

### 3. لایه‌های امنیتی

برای جلوگیری از سوءاستفاده و محدود کردن دسترسی MCP، سه لایه‌ی اصلی در نظر گرفته شده است.

#### 🔒 3.1. کاربر Read-Only برای دیتابیس

اتصال MCP به PostgreSQL با کاربر:

```text
rag_readonly
```

انجام می‌شود.

این کاربر فقط مجوز خواندن اطلاعات را دارد و امکان اجرای عملیات نوشتن روی دیتابیس را ندارد.

بنابراین حتی اگر ورودی نامعتبر یا SQL Injection وارد شود، این Connection مجوز تغییر داده‌ها را ندارد.

---

#### 🔢 3.2. محدود کردن `k`

تعداد نتایج قابل درخواست توسط Client محدود شده است.

حداکثر مقدار `k` از تنظیم:

```text
settings.mcp_max_k
```

خوانده می‌شود.

بنابراین Client نمی‌تواند مثلاً درخواست زیر را ارسال کند:

```text
k = 10000
```

و باعث دریافت تعداد بسیار زیادی نتیجه شود.

---

#### 📏 3.3. محدود کردن حجم محتوا

ممکن است یک Chunk یا صفحه‌ی بسیار بزرگ از دیتابیس برگردانده شود.

برای جلوگیری از ارسال حجم غیرضروری داده به Client، متن خروجی با تابع `_clip` محدود می‌شود.

حداکثر تعداد کاراکتر نیز از:

```text
mcp_max_content_chars
```

تعیین می‌شود.

در نتیجه حتی اگر یک صفحه مثلاً ده‌ها هزار کاراکتر داشته باشد، کل محتوای آن بدون محدودیت به Client ارسال نمی‌شود.

---

### 4. مدیریت خطاها

خطاها مستقیماً به صورت Exception خام به کاربر برگردانده نمی‌شوند.

سه حالت اصلی مدیریت شده است:

#### ورودی نامعتبر

اگر ورودی خالی یا نامعتبر باشد، پیام مشخصی برگردانده می‌شود:

```text
must be non-empty
```

#### نتیجه پیدا نشد

اگر Retrieval نتیجه‌ی قابل قبولی پیدا نکند، به جای نمایش یک خطای فنی، پیام قابل فهمی برای کاربر نمایش داده می‌شود و در صورت امکان راهنمایی لازم ارائه می‌شود.

#### خطای غیرمنتظره

خطاهای پیش‌بینی‌نشده نیز در یک لایه‌ی بالاتر Catch می‌شوند تا جزئیات خام Exception به کاربر نمایش داده نشود.

هدف این است که خروجی سیستم هم برای کاربر قابل فهم باشد و هم جزئیات داخلی پیاده‌سازی را بی‌دلیل افشا نکند.

---

## خلاصه‌ی تصمیم‌های اصلی

| بخش              | تصمیم                              |
| ---------------- | ---------------------------------- |
| `answer`         | Extractive، بدون نیاز به LLM خارجی |
| `MIN_CONFIDENCE` | `0.45`                             |
| Database User    | `rag_readonly`                     |
| محدودیت `k`      | `settings.mcp_max_k`               |
| محدودیت محتوا    | `_clip` + `mcp_max_content_chars`  |
| خطای ورودی       | پیام مشخص و قابل فهم               |
| نتیجه‌ی ناموجود  | پیام مناسب به جای Exception خام    |
| خطای غیرمنتظره   | Catch در لایه‌ی بالاتر             |

این تصمیم‌ها باعث می‌شوند سیستم در کنار عملکرد Retrieval، **قابل کنترل، قابل پیش‌بینی و امن‌تر** باشد.

### گیر: کتابخانه‌ی `mcp` در نسخه ۲ API را تغییر داده بود

با اجرای `pip install`، نسخه‌ی `2.x` کتابخانه نصب شد و API نسبت به نسخه‌های قبلی تغییر کرده بود. در این نسخه، `FastMCP` به `MCPServer` تغییر نام داده و مسیر `import` هم عوض شده بود.

نکته‌ی مفید این بود که خود کتابخانه در پیام خطا لینک **Migration Guide** را ارائه می‌کرد. این تجربه یادم داد که در کتابخانه‌های معتبر، پیام خطا معمولاً اطلاعات مفیدی برای پیدا کردن مسیر حل مشکل دارد؛ بنابراین قبل از جست‌وجوی راه‌حل، اول باید خود خطا و لینک‌های پیشنهادی آن را بررسی کرد.

در نهایت برای سازگار کردن کد با v2 فقط دو تغییر لازم بود:
